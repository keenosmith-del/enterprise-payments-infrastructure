# M01 database and access boundaries

The independent application databases are `policy_administration`, `payments_hub`, `banking_simulator` and `payroll_simulator`. A dedicated bootstrap administrator provisions each database and three roles. The non-login owner owns the database, schema and migration objects. The migration login can assume its own owner role. The runtime login can connect and read the explicitly granted foundation tables and the restricted revision view. It cannot read the Alembic administration table, create schema objects, create roles or databases, or assume the owner role. PUBLIC database connection and schema grants are revoked.

The provisioning script requires distinct application credentials. It is designed for a dedicated development cluster. It changes permissions on the cluster's `postgres` and `template1` databases and must not be applied to a shared production cluster. Each application runs its own Alembic history. The initial migration creates tenants and legal entities; the forward migration adds technical principal references and configuration. A synthetic fixture script operates under the application migration identity, uses stable UUIDs and performs idempotent upserts.

The real PostgreSQL boundary suite bootstraps twice, applies each migration twice, seeds twice, exercises the foreign key and checks cross-database connection denials for all application runtime and migration identities. The hosted stack additionally tests retained data after a normal PostgreSQL container restart. The present data model does not contain journals or payment processing records.
