# M00 architecture assessment

Revision 0.1 | 26 November 2026 | EPI 0.1.0 | Proposed for maintainer review.

## Ownership and deployment

The project implements four independent applications (FR-001 to FR-025). The Policy Administration System (PAS) owns policies, products, billing schedules, receivables, approved claims and policy allocations. The Enterprise Payments Hub owns canonical acceptance, mandates it administers, scheduling, execution attempts, the control journal, reconciliation, settlement allocations and resolution cases. The Banking and Payment Network Simulator owns provider credentials and synthetic accounts, operation execution, status enquiry, balances and independently generated statements. The Employer and Payroll Simulator owns employment and deduction eligibility, payroll cycles, item deductions and remittance evidence. The Hub records observations of the last two systems, with source references, without imposing their outcomes.

Each application deploys and migrates independently. Start with four databases in one development PostgreSQL instance, plus separate infrastructure metadata databases when needed. Revoke default database CONNECT and grant only role-specific access. Give every application a non-login object owner, a distinct migration identity and a runtime identity with the minimum schema permissions. Runtime roles have no create database, create role, ownership or cross-database privileges. Foreign data wrappers and cross-application SQL are outside the topology. Shared infrastructure implies a shared failure domain. Compare separate instances if recovery or independent resource limits justify them.

Keep intake, authority, orchestration, journal, reconciliation, allocation and cases within the Hub's single transactional database. Run API, relay and workers as independent processes over the same application boundary. Allow cross-module writes only through owner interfaces inside a defined unit of work. A single transaction may reserve amount, change attempt state and insert an outbox record. Broker publish, SFTP transfer, provider calls and PAS application occur beyond that transaction. Avoid service extraction until operational evidence establishes a need. Shared packages can define wire representations, exact technical types, observability and UI components. They cannot own an application aggregate or embed application data access.

## Contract and recovery boundaries

HTTP intake derives tenant and actor from validated identity and sender mapping, issues a durable receipt only after acceptance commits, and exposes a receipt or status read. Protected status reads enforce the same tenant and legal entity scope as writes. Define stable error classes for invalid payload, conflict, insufficient authority, unavailable dependency and unknown outcome. Broker delivery carries schema version, event ID, type, producer, tenant, legal entity, subject reference, occurrence time, aggregate version, causation and correlation. Correlation joins evidence and is independent of deduplication. Restrict producer and consumer identities to their own exchanges, bindings and queues. Outbox relay preserves event identity after uncertain confirmation. Consumer inbox and domain result commit together before acknowledgement. Bound retries by failure class and use an explicit quarantined state for permanent failures. Replays preserve lineage, record operator, reason and policy, and cannot override a payment hold.

SFTP uses separate partner accounts, key authentication, verified host keys and a constrained transfer directory. An upload arrives under a staging name. Import starts only after same-filesystem promotion and manifest availability. The manifest declares partner batch ID, contract version, content digest, count, currency-specific control totals and framing. Validate encoding, fields, duplicate rows, tenant binding and manifest before accepting any rows. Store the original and receipt independently from financial acceptance. Same source identity and digest yields original receipt. A changed digest becomes a conflict or an explicit revision under review. File receipts, row acceptance, execution results and settlement observations have separate contract types.

A provider observation can arrive in a response, through independent enquiry, or in later evidence. Preserve its channel, raw code, provider reference, source version and observation time. Expired leases resume the prior operation identity. If status cannot be established, keep the reservation and hold the case. Settlement facts are independently imported with source revision, transaction date, value date, currency, amounts and provenance. Evidence contradictions are quarantined. A successful result delivered to PAS requires a separate durable consumer receipt before PAS application is considered confirmed.

## Identity, lineage and operational containment

Use access tokens validated for issuer, audience, signature, lifetime and appropriate actor claims. Model interactive and service principals separately. Scope reads, writes, subscriptions and exports at the application boundary, then add database and infrastructure controls. Require distinct authenticated principals for sensitive approval. Capture checks against a stable approval subject version so changes invalidate the prior approval. Trace IDs connect work across transports. Do not put account, mandate or identity material in spans. Track queue age, relay lag, ambiguous attempts, reconciliation divergence, SFTP backlog, analytical freshness and error classes.

The integration service validates, routes and maintains receipts without acquiring financial authority. Data engineering consumes published records or authorised versioned snapshots, lands immutable raw data, validates into canonical datasets, and publishes curated cohorts with transformation and source versions. The reporting database and BI identities receive curated read access only. An analytics outage delays publication while operational processing continues. A broker outage preserves committed outbox work. A bank enquiry outage prevents unsafe fallback. A restore requires provider and payroll evidence reconciliation before dispatch resumes.

## Decision dispositions and approval conditions

- ADR-P01. Recommend independent databases and runtime roles in one local cluster. Platform owner must demonstrate denied cross-database access for all four identities and isolated migration ownership before acceptance.
- ADR-P02. Recommend modular transactional Hub. Hub owner must prove atomic posting and outbox, module write rules and a recovery path. Compare extraction only after a measurable isolation or scaling need.
- ADR-P03. Recommend Python and PostgreSQL. Platform and finance owners must approve wheel/image locks and actual database arithmetic, constraints, contention and recovery tests.
- ADR-P04. Recommend at-least-once delivery, durable outbox and inbox. Integration owner must prove broker confirmation, redelivery and commit-before-ack with stable identity. Kafka retained-stream semantics are deferred pending a workload that requires them.
- ADR-P05. Recommend separate PAS accounting and non-custodial Hub controls. Finance owner must approve journal accounts, posting matrix, period rules and correction authority before dispatch.
- ADR-P06. Recommend independent obligation, execution and settlement evidence. Finance and simulator owners must approve source contracts, partial matching, fee and reversal treatment. Payroll deduction and remittance are additional corroborating evidence.
- ADR-P07. Recommend versioned operational exports, Parquet and curated reporting. Data owner must demonstrate replay, late corrections and lineage. Power BI runtime and object-storage selection remain open.
- ADR-P08. Recommend actual transports and synthetic rails. Integration and security owners must prove transport credentials, SFTP restrictions, provider enquiry and failure recovery before gateway acceptance.
- ADR-P09. Recommend deterministic core. Data owner may propose optional models under M21 with frozen baseline comparisons and zero financial privileges.

Maintain these as proposed dispositions against the [original decisions](../../ARCHITECTURE_DECISIONS.md). Maintainer approval is required. M00-D01 proposes per-database credentials on a shared local cluster with platform ownership and deny tests. M00-D02 proposes durable receipt versus execution and settlement semantics across all transports, owned by integration and finance, subject to compatibility and recovery tests. M00-D03 proposes profile-based local infrastructure and a curated browser BI fallback, owned by platform and data engineering, subject to resource and lineage checks. Open contract questions include canonical schema extensibility, provider enquiry consistency thresholds, partner batch revision policy, journal adjustment approval and data retention. Owners respectively are integration, simulator, integration, finance and data/security. Each decision is due before the first dependent implementation.
