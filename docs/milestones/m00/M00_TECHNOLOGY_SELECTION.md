# M00 technology selection

Revision 0.1 | 26 November 2026 | EPI 0.1.0 | Proposed candidates, pending maintainer approval.

## Backend and dependency management

For M01, target CPython 3.12 for the compatibility proof because 3.12.15 executed on this Mac and the dependency ecosystem publishes compatible wheels. Python 3.12 is in security maintenance. Reassess the support horizon against Python 3.13 before freezing the application baseline. The default Python 3.15.1 also executed the version command, but it is outside the verified dependency range of the Arrow release considered here. Choose Python over Java/Spring and C#/.NET for one shared numerical, API and analytical language. Python's dynamic runtime makes explicit validation, type checks and regression coverage important. Exact money uses Decimal for rates and integer minor units for persisted value.

Evaluate FastAPI, Pydantic 2, SQLAlchemy 2.0, Alembic 1 and psycopg 3. FastAPI provides an HTTP and OpenAPI boundary. Pydantic validates schema versions, refuses coercion of material financial fields and generates boundary schemas. SQLAlchemy owns transactions and query construction, with explicit SQL for locks and database constraints when appropriate. Alembic owns revisioned migrations per database. FastAPI, Pydantic, SQLAlchemy and Alembic are MIT-licensed upstream. psycopg is LGPL-3.0. Confirm adapter distributions and transitive notices before publishing. Flask would need additional contract and validation assembly. A Django-based stack couples more framework conventions to app boundaries. SQL-first is useful for financial enforcement, while hand-maintained migrations alone would add schema-drift overhead.

Use pyproject metadata per Python project with a maintainable workspace lock and hashes. Evaluate uv (MIT or Apache-2.0) with a pip-compatible export for restricted environments. Use Ruff (MIT) and mypy (MIT) for lint and checking. Run a clean sync and type check in every supported platform. Measure memory per API/worker and bound DB connection pools. Pin the resolved versions after wheel, advisories, licence and runtime checks. Install only binary-compatible native dependencies for CI, or document a source build with explicit toolchain.

See the [Python lifecycle](https://devguide.python.org/versions/), [Arrow compatibility guide](https://arrow.apache.org/docs/20.0/python/install.html), [FastAPI source](https://github.com/fastapi/fastapi), [Pydantic source](https://github.com/pydantic/pydantic), [SQLAlchemy source](https://github.com/sqlalchemy/sqlalchemy), [Alembic source](https://github.com/sqlalchemy/alembic) and [psycopg source](https://github.com/psycopg/psycopg).

## PostgreSQL and financial persistence

Use PostgreSQL 17 as the probe line (PostgreSQL licence), with the official `17-bookworm` image candidate. Compare a shared cluster with dedicated databases against per-app instances. A shared cluster uses less memory but has a shared blast radius. Separate role ownership and revoke default connection grants. Use uniqueness, composite foreign keys, amount constraints, restricted posting privileges and explicit row locking. Use serializable transaction retry only for the full local transaction and distinguish serialization failure from unrelated exceptions. SQLite is suitable for the isolated provider fixture; the production transaction tests require PostgreSQL. Plan per-database logical backup and independent restore validation before simulating loss. Full cluster point-in-time recovery needs a documented retention and restore drill. Set conservative connection and memory limits and measure peak usage instead of adopting benchmark targets as capacity claims. Verify the image digest, native ARM64 support, exact arithmetic, two-client contention, database denial and restore. Adopt the database boundary in M01 and posting controls in M02. See [transaction isolation](https://www.postgresql.org/docs/17/sql-set-transaction.html), [whole-transaction retries](https://www.postgresql.org/docs/17/mvcc-serialization-failure-handling.html) and the [official image](https://hub.docker.com/_/postgres).

## Integration

RabbitMQ 4.2 is the evaluated broker line (MPL-2.0 for core). Use durable queues and persistent delivery, publisher confirms, manual acks, bounded retry and quarantine. Confirming publication and acknowledging consumption prove different events. The application outbox and inbox maintain business durability through broker failures. Kafka adds a retained log and consumer partitioning model that needs a distinct replay and operational design. Use RabbitMQ at M01 for startup and M04 for business integration. Validate platform image, resource caps, confirms, consumer redelivery, dead letters, permissions and restart behaviour. Compare classic queues in disposable probes with quorum queue topology before making availability claims. See the [broker confirms guide](https://www.rabbitmq.com/docs/confirms), [RabbitMQ licence](https://github.com/rabbitmq/rabbitmq-server/blob/main/LICENSE) and [official image](https://hub.docker.com/_/rabbitmq).

Use actual OpenSSH SFTP (BSD-style upstream licensing) with key authentication, known hosts, per-partner jailed directories and constrained service accounts. Compare managed SFTP only if equivalent local reproduction is available. Do not publish service ports outside the development host. SFTP is a byte transport and does not validate a financial record. Verify transfer, duplicate digest, partial-file state, invalid manifests and account isolation. Adopt profiles at M01, full exchange at M04. See [OpenSSH server configuration](https://man.openbsd.org/sshd_config.5).

Use a Python ESB service and explicitly versioned REST/OpenAPI 3.1, AsyncAPI 3 and partner file schemas. OpenAPI describes request, receipt and status contracts; AsyncAPI describes message exchange; CSV and XML get separate schema and manifest versions. Contract schemas and sanitised fixtures are versioned independently of application builds. A proprietary ESB would increase licence and runtime complexity. Avoid paid connector suites and defer Kafka and Redis. Keep partner transformations outside financial authority and preserve original bytes, source codes and schema versions. Verify transport equivalence and authentication in M04. See the [OpenAPI specification](https://spec.openapis.org/oas/v3.1.1.html) and [AsyncAPI specification](https://www.asyncapi.com/docs/reference/specification/v3.0.0).

## Frontend and identity

Evaluate React 19 (MIT), TypeScript 5.9 (Apache-2.0) and Vite 7 (MIT) against Node 24.21.0 and npm 11.19.0, both observed locally. Vite 7 documents Node 20.19+ or 22.12+; run build and type checks on the selected maintained Vite line before locking. Compare a server-rendered framework only if deployment or UI needs warrant a server in every interface. Use shared accessible controls, separate entry points and rendered receipt and status evidence. No client-side financial authority. Use npm lockfiles and separate build/type checks. Measure build and browser memory. Introduce frontend tooling in M01 when the framework lock is agreed and add operational journeys at their dependent milestones. See the [Vite runtime prerequisites](https://v7.vite.dev/guide/) and [Node.js release schedule](https://nodejs.org/en/about/previous-releases).

Evaluate Keycloak 26 (Apache-2.0) for OIDC/OAuth, audience mapping, interactive and service identity separation and scoped administration. Use an independent identity database and keep app-specific authorisation in each owning service. Choose code flow with PKCE for browser sessions and client credentials or a stronger non-interactive identity for services. Avoid local bearer token issuers outside isolated tests. Compared with a cloud identity service, Keycloak improves local repeatability and costs more memory and maintenance. Use a small development realm and perform startup, versioned import, failure, key rotation and interface denial tests. Production mode concerns include TLS, proxy headers and database configuration. Adopt identity skeleton in M01 and exercise maker/checker and tenant isolation throughout. See [container setup](https://www.keycloak.org/server/containers) and [production configuration](https://www.keycloak.org/server/configuration-production).

## Analytics and business intelligence

Use versioned exports into S3-compatible raw and canonical storage, Parquet via PyArrow, optional Polars for bounded transformations, DuckDB and versioned SQL for checks, and a curated PostgreSQL reporting schema. PyArrow and Parquet are Apache-2.0. DuckDB and Polars are MIT. The isolated probe candidates are PyArrow 20.0.0 and DuckDB 1.4.3, subject to successful installation and runtime checks. Compare filesystem development storage, SeaweedFS (Apache-2.0) and MinIO (AGPL-3.0 for upstream server). Require affirmative verification of licence obligations, maintained container supply, reproducible ARM64 image and S3 semantics before selecting an object store. A local filesystem cannot stand in for object-store credential or atomic-publication verification. Use a small Python runner before considering orchestration or dbt. Constrain analytical reads and memory independently of operational services. Capture duplicates, late observations and raw-to-curated versions in M17 according to the roadmap. See the [Arrow documentation](https://arrow.apache.org/docs/python/), [DuckDB Parquet support](https://duckdb.org/docs/stable/data/parquet/overview) and [SeaweedFS source](https://github.com/seaweedfs/seaweedfs).

Power BI Desktop is proprietary and requires a supported Windows environment, including a specific update for Windows on ARM. Demonstrate on supported Windows if available and verify report sharing and refresh entitlements before making deployment promises. Use curated SQL and portable extracts to support a browser-based operational demonstration on macOS. Validate warehouse reconciliation, freshness, row scope and report filters independently of the BI client. See [Microsoft Desktop requirements](https://learn.microsoft.com/en-ie/power-bi/fundamentals/desktop-get-the-desktop).

## Platform and verification

Use Compose profiles for scoped local startup and GitHub Actions for fresh runner verification. Compose CLI is Apache-2.0 and Docker Desktop has separate commercial terms. Confirm team eligibility and verify ARM64 and Linux runner image digests. Hosted CI has private repository usage limits. Keep third-party workflow actions pinned by commit; grant read-only checkout and use ephemeral credentials. Verify reproduction from an empty cache, migrations and exact successful workflow commit. M00 adds the isolated workflow definition. M01 establishes wider release checks.

Use OpenTelemetry (Apache-2.0) for traces and metrics, Prometheus (Apache-2.0) for pull-based operational metrics and Grafana OSS (AGPL-3.0) for local series and alert exploration. Compare structured logs as the minimum stack and keep dashboards optional during low-memory development. Reject high-cardinality tenant, customer or payment IDs in metric labels. Protect dashboard endpoints and measure collector overhead. Adopt basic telemetry in foundation and build dashboards when signal producers exist. See [OpenTelemetry documentation](https://opentelemetry.io/docs/), [Prometheus source](https://github.com/prometheus/prometheus) and [Grafana licensing](https://grafana.com/licensing/).

Evaluate pytest (MIT) for suites, Hypothesis (MPL-2.0) for invariants, Testcontainers Python (MIT) for isolated DB and broker fixtures, Playwright (Apache-2.0) for actual operator journeys and Locust (MIT) for measured load. Compare Compose-managed services in CI with per-test containers for isolation and runtime cost. Run tests with architecture-specific binaries and bounded concurrency. Add pip-audit and npm audit after lock installation, secret scanning before publication, and OS image scanning after image locks. Review transitive advisories with context and make critical security defects blockers. Add core testing in M01, financial properties in M02 and load/recovery in M20. No load or resource claims flow from M00 prototype timings.
